# RootSleuth Operations Console Deployment Guide

English | [简体中文](OPERATIONS_DEPLOYMENT_GUIDE.md)

> Scope: the whole RootSleuth project — the operations console `app/` (React + Vite frontend + FastAPI backend + Atoms Cloud managed PostgreSQL) and the RAG pipeline `aiops-rag-system/` (Python, with Milvus/Kafka/Redis/ES docker-compose); the two are deployed independently.
> Project-level documentation lives under `docs/` (the directory containing this guide); see the root `README.md` for the directory layout.

## 1. System Composition

| Component | Directory | Stack | Default Port |
|-----------|-----------|-------|--------------|
| Frontend | `app/frontend` | React 18 + Vite + shadcn/ui + Tailwind | 3000 (auto-avoids conflicts) |
| Backend | `app/backend` | FastAPI + SQLAlchemy async + pydantic-settings | 8000 (auto-avoids conflicts) |
| Database | Atoms Cloud managed | PostgreSQL (ORM auto-creates tables) | - |
| Auth | Atoms platform | OIDC + JWT (demo-login additionally available in demo environments) | - |

## 2. Environment Requirements

- Node.js ≥ 18, package manager pnpm (scripts fall back to npm when missing).
- Python 3.10+, dependency management via uv (`uv venv` + `uv pip install`).
- Backend dependency lists: `app/backend/requirements.txt` and `requirements.default` (both must be installed; the startup script handles them in order).

## 3. One-Command Startup (Development/Preview)

```bash
bash app/start_app_v2.sh
```

Script behavior:
1. Auto-detects the local IP and an available port pair (backend starts from 8000, frontend from 3000; when occupied it retries with +1, up to 3 times).
2. Installs backend dependencies (uv) and frontend dependencies (pnpm install + `@metagptx/web-sdk@latest`).
3. Starts the backend: `uvicorn main:app --host 0.0.0.0 --port $BACKEND_PORT --reload` (excluding *.log, *.pyc).
4. Starts the frontend: `pnpm dev --host 0.0.0.0 --port $FRONTEND_PORT` (Vite proxies `/api` to the backend port).
5. Polls `GET http://$LOCAL_IP:$BACKEND_PORT/health` until ready (up to 60 seconds).
6. Ctrl+C stops both frontend and backend together (trap cleanup).

Common parameters:
- `--no-start`: install dependencies only, without starting.
- `--local`: local mode, replacing the `$$BACKEND_DOMAIN$$`/`$$FRONTEND_DOMAIN$$` placeholders with local addresses.
- `--env-filename FILE`: specify the env file (default `.env`; file mode is enabled when no S2S parameters are provided).
- Environment-variable mode: when `S2S_JWT_TOKEN`, `S2S_JWT_BASE_URL`, and `CHAT_ID` are provided, configuration is pulled from the platform API (fixed to the dev environment, with dirty-signal hot refresh).

## 4. Independent Frontend/Backend Startup

Backend (under `app/backend`):

```bash
uv venv && source .venv/bin/activate
uv pip install -r requirements.txt
uv pip install -r requirements.default
export IS_LAMBDA=false
uvicorn main:app --host 0.0.0.0 --port 8000
```

Frontend (under `app/frontend`):

```bash
pnpm install
BACKEND_PORT=8000 pnpm dev        # Development mode, /api proxied to the backend
BACKEND_PORT=8000 pnpm build      # Production build, output in dist/
```

> For production builds that need to prerender `/` and `/blog/`, keep the existing prerender plugin configuration in `vite.config.ts`; prerender data is generated by the `prerender/` scripts.

## 5. Database Initialization and Seed Data

1. **Table creation**: on backend startup the ORM automatically creates all business tables (events, kb_cases, kb_change_sets, kb_versions, kb_merge_proposals, approval_requests, approval_steps, rule_versions, unknown_templates, audit_logs, console_configs) — no manual SQL required.
2. **Demo seed** (preview/demo environments):

```bash
cd app/backend
python scripts/seed_console_demo.py
```

3. **Sequence synchronization (important)**: the seed script inserts with explicit IDs, so PostgreSQL auto-increment sequences do not advance, which causes primary key conflicts on later INSERTs (typical symptom: approval/promotion APIs return 500). Run:

```bash
python scripts/fix_sequences.py
```

This script resets the id sequences of 11 tables to `MAX(id)+1`. **It must be run once after any explicit-ID data import.**

## 6. Environment Variables

The backend reads environment variables via `core/config.py` (pydantic-settings); keys not explicitly declared can be read dynamically via `settings.<name>` (snake_case → UPPERCASE environment variable).

| Variable | Description |
|----------|-------------|
| `IS_LAMBDA` | Fixed `false` (local/self-hosted); when true, the Lambda entry `lambda_handler.py` is used |
| `ENVIRONMENT` | Environment identifier, `dev` locally |
| `BACKEND_PORT` / `FRONTEND_PORT` | Auto-assigned and exported by the startup script, overriding same-named .env values |
| `S2S_JWT_TOKEN` / `S2S_JWT_BASE_URL` / `CHAT_ID` | Platform configuration pull credentials (optional; when provided, environment variables are pulled from the API) |
| `USERNAME` | Platform debug request header (optional) |

Authentication secrets are injected by the Atoms platform (OIDC/JWKS) and need no manual configuration; AI capabilities go through the built-in AIHub and require no self-provided API key.

> **Diagnosis determinism configuration (variance governance)**: the diagnosis Agent's sampling temperature is not managed through environment variables but through the configuration center's `diagnose_temperature` key in `console_configs` (default `0`). Keep the default 0 in production to guarantee that repeated deep diagnoses of the same event produce stable output (model, retrieval, and tool traces are reproducible); raise it only for multi-path exploration. Changes take effect immediately and write a `config_update` audit record; see DIAGNOSE_AGENT_DESIGN.md §8.

> **Diagnosis wall-clock budget (Cloudflare 502 protection)**: the overall diagnosis duration is likewise governed by the configuration center key `diagnose_time_budget_seconds` (default `90` seconds, range 30~600). The budget now bounds both the deep-diagnosis and single-round diagnosis paths: for deep diagnosis, multi-round ReAct reasoning, every in-loop LLM call (its timeout is truncated against the remaining budget), the forced conclusion, and the single-round degradation (which inherits the remaining budget as a deadline) are all bounded; the direct single-round route (POST /events/{id}/diagnose, including the embedding semantic boost and two LLM attempts) reads the same key. When the remaining budget is insufficient the system stops reasoning and moves to conclusion; when the budget is exhausted it returns a structured 502 (`diagnose_time_budget_exhausted`), preventing request durations from stacking past edge proxies (e.g. Cloudflare's default 100s) or Nginx timeouts when the LLM slows down. In production, the budget should be smaller than the shortest timeout in the chain (edge proxy < Nginx `proxy_read_timeout` < application internal timeouts); deployments behind Cloudflare are advised to keep the default 90 or lower. Changes take effect immediately and write a `config_update` audit record.

> **Per-Agent LLM access (configuration center)**: the diagnosis / knowledge governance / on-call Agents all support independent LLM runtime parameters, with keys `<agent>_llm_provider` / `<agent>_llm_base_url` / `<agent>_llm_api_key` / `<agent>_llm_model` / `<agent>_llm_timeout_seconds` (`<agent>` ∈ `diagnose` / `kb_governance` / `oncall`) plus independent temperatures (`diagnose_temperature` / `kb_governance_temperature` / `oncall_temperature`). **When left empty, every key inherits the global `llm_*` configuration item by item**, and you can override only some of them (e.g. change just the API key or Base URL for the diagnosis Agent); API keys are persisted Fernet-encrypted server-side and displayed masked. Each Agent group in the configuration center offers a connectivity test (returning the resolved model/timeout/provider and access_source); all parameters are read from the database in real time on every request, so changes take effect immediately without restart.

### 6.1 RAG Pipeline Environment Variables (aiops-rag-system/)

The RAG service is a separate process (reading environment variables via `src/config.py`); see `aiops-rag-system/.env.example` for the full template. Core service-to-service authentication and multi-tenancy items (P0):

| Variable | Description |
|----------|-------------|
| `RAG_AUTH_ENABLED` | Master auth switch; when `false` or when no keys are configured, auth is off (compatible with existing deployments; anonymous requests pass as the default tenant) |
| `RAG_API_KEYS_JSON` | JSON mapping key → `{name, tenant_id, scopes}` (shorthand `{"<key>": "console"}` supported). `read`=retrieval/verification/observability (kb-search, kb-sync/verify, kb-cache/status, diagnostic); `write`=kb-sync upsert/delete, kb-cache/invalidate, feedback, cases/close. After configuration: missing/wrong key → 401, missing scope → 403 |
| `RAG_DEFAULT_TENANT` | Default tenant when identity lacks one (default `default`). `default` is the public knowledge layer: tenant t sees `{default, t}`, non-default tenants cannot see each other → cross-tenant unauthorized recall rate 0% |
| `LLM_API_KEY` / `EMBEDDING_API_KEY` | LLM and Embedding credentials, injected via platform secret management |

Production requirements: `RAG_AUTH_ENABLED=true` with keys configured by minimal scope; the console backend passes `X-API-Key` through the `rag_api_key` configuration when calling RAG (see `app/backend/services/rag_sync.py`, `console_agent.py`); `/api/v1/webhook` keeps its unauthenticated contract. Verification:

```bash
# Missing key should 401; wrong key should 401; a key without write scope calling a write API should 403
curl -i http://localhost:8080/api/v1/kb-search -X POST -H 'Content-Type: application/json' -d '{}'
curl -i -H "X-API-Key: <console-key>" http://localhost:8080/api/v1/kb-sync/verify/E2E-CASE-1
```

## 9. Production Deployment Essentials

1. **Frontend static hosting**: `pnpm build` produces `dist/`, hosted directly by Nginx/gateway as static files.
2. **Backend daemon**: drop `--reload` in production and use systemd / supervisor / containers:

```ini
# systemd example (/etc/systemd/system/aiops-console.service)
[Service]
WorkingDirectory=/opt/app/backend
Environment=IS_LAMBDA=false
ExecStart=/opt/app/backend/.venv/bin/uvicorn main:app --host 0.0.0.0 --port 8000 --workers 2
Restart=always
```

3. **Reverse proxy (Nginx example)**:

```nginx
server {
    listen 443 ssl;
    server_name console.example.com;

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
    location / {
        root /opt/app/frontend/dist;
        try_files $uri /index.html;   # SPA route fallback
    }
}
```

- The callback domain must match the Atoms OIDC app configuration; use HTTPS uniformly.

## 10. Backup and Restore

```bash
# Backup (business database)
pg_dump "$DATABASE_URL" -Fc -f console_backup_$(date +%F).dump

# Restore
pg_restore --clean --if-exists -d "$DATABASE_URL" console_backup_2026-09-11.dump
python scripts/fix_sequences.py   # Synchronize sequences after restore
```

- Audit logs (audit_logs) are compliance data; include them in daily backups and retain ≥ 180 days.
- Knowledge case historical versions (kb_versions) and rule versions (rule_versions) are append-only; after backup they remain traceable at any time.

## 11. Upgrade and Rollback

1. **Upgrade**: pull new code → install dependencies (backend uv / frontend pnpm) → restart the backend (ORM automatically adds new tables/columns) → rebuild the frontend and replace dist. Take a §10 backup before upgrading.
2. **Application rollback**: switch back to the previous code version and restart; if database structure changes are backward-compatible additions only, no database rollback is needed.
3. **Data rollback**: prefer the console's built-in capabilities for business-semantic rollback (knowledge case version rollback, rule version rollback) — safer than direct database edits and with built-in auditing.
4. **Sequence repair**: run `scripts/fix_sequences.py` after any explicit-ID import/restore.

## 12. Troubleshooting

| Symptom | Investigation and Handling |
|---------|---------------------------|
| Backend won't start | Check `logs/restart.log` and `logs/app_*.log`; confirm both requirements files are installed and `.venv` is activated |
| Port occupied | The script auto-avoids with +1; for manual startup verify `BACKEND_PORT`/`FRONTEND_PORT` |
| Approval/promotion 500 primary key conflict | Run `python scripts/fix_sequences.py` (explicit-ID seeding left sequences unsynchronized) |
| Frontend 401 / login loop | Confirm login goes through the SDK (localStorage `token`); check the callback route `/auth/callback` and the OIDC domain configuration |
| All AI diagnoses timeout | Raise `llm_timeout_seconds` in the configuration center; confirm the platform AIHub is available |
| RAG returns nothing | Knowledge base is empty or all cases are archived; run the seed script or add active cases |
| Rule publish has no effect | Check the rule version list for the target version status=active; an audit `rule_reload` record means hot reload succeeded |
| Frontend /api 404 | In development mode confirm the Vite proxy target port equals the backend's actual port (`BACKEND_PORT`) |

## 13. Security Notes

- Evaluate before disabling the convenience channel in production (`/api/v1/auth/demo-login` should only exist in preview environments).
- Default role `viewer` is least-privilege; bind roles by exact email in `role_bindings_json`.
- All write operations (approvals/publish/rollback/config) are force-audited; bypassing the console to edit the database directly is forbidden.
- Database connection strings and platform secrets live only in environment variables/platform secret management; never commit them to the repository.

## 15. PostgreSQL Production Hardening

### 15.1 Account and permissions (self-hosted)
```sql
CREATE ROLE aiops_console LOGIN PASSWORD '<strong password>';
CREATE DATABASE aiops_console OWNER aiops_console;
GRANT ALL ON SCHEMA public TO aiops_console;   -- ORM startup auto-creation needs DDL
```
- The connection string goes into `DATABASE_URL` (`postgresql+asyncpg://aiops_console:<password>@<host>:5432/aiops_console`).
- Atoms Cloud managed databases get the connection string injected by the platform; no manual grants needed.

### 15.2 Alembic migrations
```bash
cd app/backend
alembic current              # Current version (should be b8f2c1d4e5a6: users.status)
alembic upgrade head         # Upgrade to latest
alembic history --verbose    # Migration history
alembic downgrade -1         # Roll back one version (back up first, see §10)
```
- ORM auto-creation and Alembic coexist: new tables are created by the ORM at startup; structural changes go through migrations.

### 15.3 Verification commands
```bash
psql "$DATABASE_URL" -c "\dt"                                          # Table list
psql "$DATABASE_URL" -c "SELECT count(*) FROM audit_logs;"             # Row count spot check
psql "$DATABASE_URL" -c "SELECT version_num FROM alembic_version;"     # Migration version
python scripts/fix_sequences.py                                        # Required after explicit-ID import/restore
```

## 16. Milvus Vector Store Deployment (etcd + MinIO + Milvus)

### 16.1 Topology and connection parameters
- Components: etcd v3.5.14 (metadata) + MinIO RELEASE.2024-05-01 (object storage) + Milvus v2.4.4 standalone, orchestrated in `aiops-rag-system/docker-compose.yml` with data volumes `etcd_data`/`minio_data`/`milvus_data`.
- Connection parameters (`aiops-rag-system/.env`): `MILVUS_HOST=localhost`, `MILVUS_PORT=19530`, `MILVUS_COLLECTION=aiops_knowledge_base`, `MILVUS_NPROBE=32`.

### 16.2 Collection and index specifications
- Collection `aiops_knowledge_base`: primary key `case_id VARCHAR(64)`; vector field `embedding FLOAT_VECTOR dim=1024` (BGE-M3); shards_num=2.
- Indexes: vector `IVF_SQ8 / COSINE / nlist=4096`; scalar TRIE indexes on `fingerprint`, `service_name`, `error_type`, `cluster`.
- Partitions: monthly `p_YYYYMM`; retrieval targets the last 3 months' partitions.

### 16.3 Initialization and verification
```bash
cd aiops-rag-system
docker compose up -d etcd minio milvus
docker compose ps                        # Three containers Up
curl -s http://localhost:9091/healthz    # -> ok
python scripts/init_milvus.py            # Idempotent creation of collection/indexes/last-3-month partitions
python scripts/seed_cases.py             # Seed cases (optional in demo environments)
```
- Risky operation: `python scripts/init_milvus.py --overwrite` deletes and recreates the collection — forbidden in production.

### 18.4 Rolling upgrade and rollback
```bash
kubectl set image deploy/aiops-console-backend backend=registry.example.com/aiops-console-backend:<new tag>
kubectl rollout status deploy/aiops-console-backend   # Watch the rollout; it blocks when stuck
kubectl rollout history deploy/aiops-console-backend  # Version history

```
- Pre-upgrade steps: pg_dump backup (§10) → confirm migrations are backward-compatible additions only (new columns/tables need no DB rollback).

| etcd | quay.io/coreos/etcd:v3.5.14 | 2379 (container network) | Milvus metadata store | Quota 4GB (`ETCD_QUOTA_BACKEND_BYTES`), auto compaction | Milvus unavailable → diagnosis degrades to context-free direct answers |
| MinIO | minio/minio:RELEASE.2024-05-01 | 9000 (container network) | Milvus object storage (vector data on disk) | Default credentials minioadmin (intranet deployment; change in production) | Same as above |
| Milvus | milvusdb/milvus:v2.4.4 standalone | 19530 gRPC / 9091 healthz | Vector retrieval: HNSW/IVF_SQ8, dim=1024 (BGE-M3), monthly partitions, last-3-month retrieval | Collection `aiops_knowledge_base`, specs in §16.2 | Diagnosis degradation (is_fallback=true, LLM answers directly) |
| Kafka | bitnami/kafka:3.4 (KRaft single node) | 9092 | Alert event decoupling buffer, decouples standardization from the three consumers | Topic `standardized-events`; PLAINTEXT (intranet) | Events stay staged in Redis, not lost; stalled consumption needs scaling/skipping |
| Redis | redis:7.0-alpine (AOF) | 6379 | Fingerprint dedup (TTL debounce), event staging (TTL 7 days), CMDB topology cache (1h), 5-min window aggregation | `REDIS_URL=redis://localhost:6379/0` | Dedup fail-open: alerts are not lost but may duplicate |
| Elasticsearch | elasticsearch:8.12.2 single node | 9200 | Cold storage and audit buffer (standardized event archive) | heap 512MB (`ES_JAVA_OPTS`), no security plugins (intranet) | Only cold storage/audit missing; main path unaffected |
| PostgreSQL | Atoms Cloud managed or self-hosted | 5432 | Console business database (11 business tables + users) | Connection string `DATABASE_URL`, see §15 | Console unavailable; pipeline unaffected |

### 21.3 Data flow

1. External monitoring systems call `POST /api/v1/webhook`; the standardization engine performs Drain template extraction + rule classification (target P99 < 10ms) and generates `event_id` and the fingerprint.
2. Events are synchronously written to Redis (TTL 7 days, for human diagnosis / alert closed-loop queries) and published to the Kafka `standardized-events` topic.
3. **Dedup Consumer**: Redis fingerprint SETNX debounce + 5-minute window counters; bursts escalate severity automatically before pushing to ChatOps.
4. **RAG Consumer**: BGE-M3 vectorization → Milvus last-3-month partition dual-path recall → cosine/topology/time-decay/feedback composite reranking → Few-shot prompt → LLM with enforced JSON output (automatic degradation on timeout/error).
5. **Storage Consumer**: events are written to ES cold-storage indexes (on ES failure, buffered in memory then discarded, audit only).
6. Human feedback (`POST /api/v1/feedback`) writes back to Milvus case scores influencing reranking; alert closure (`POST /api/v1/cases/close`) writes root cause/remediation into the knowledge base, forming the closed loop.
7. The console plane provides human operations, approvals, and rule governance through its own PostgreSQL and AIHub; it is independent of the pipeline middleware.

## 23. External System Integration and Post-Diagnosis Notification Push

### 23.1 Event ingest API (upstream alerts → console events table)

- Routes: `POST /api/v1/ingest/alerts` (single) and `POST /api/v1/ingest/alerts/batch` (batch ≤ 200).
- The payload is compatible with the RAG webhook contract (source/raw_message/labels/timestamp); UMPS, Prometheus Alertmanager forwarding, and similar upstreams can integrate directly.
- Idempotency: deduplication by event_id (an external event_id takes precedence; when absent, `evt_{epoch ms}_{first 8 of fingerprint}` is generated); the fingerprint matches the RAG webhook convention: `md5(source|service|error_type)`.
- Auth: when the configured `event_ingest_token` is non-empty, requests must carry an exactly matching `X-Ingest-Token` header (401 otherwise); when empty, requests pass through (fail-open).

| Payload field | Required | Mapping/notes |
|---------------|----------|---------------|
| source | No (default webhook) | Upstream identifier; part of the fingerprint |
| raw_message | Recommended | Raw alert text, stored as raw_log; used for keyword classification |
| labels | No | Service/cluster extraction (service/service_name/app/job, cluster/k8s_cluster); alertname as the template fallback |
| timestamp | No | Millisecond/second epoch or ISO string, stored as created_at |
| event_id | No | External event ID, the idempotency key |
| error_type | No | When absent, keyword classification applies (gateway 502 / OOM / connection refused / disk full / CPU throttling / Redis pool exhausted / timeout) |
| template | No | Falls back to labels.alertname or the first 120 chars of raw_message |
| severity | No | Integer 1/2/3 → info/warning/critical; common text aliases mapped to the nearest level; default warning (a hit classification uses its default level) |
| confidence / topology | No | Written to the corresponding event columns |
| service_name / cluster / namespace | No | Explicit fields take precedence over labels; namespace is the last cluster fallback |

```bash
# Single alert
curl -X POST http://127.0.0.1:8000/api/v1/ingest/alerts \
  -H "Content-Type: application/json" -H "X-Ingest-Token: <event_ingest_token>" \
  -d '{"source":"webhook","raw_message":"Pod payment-7d9 OOMKilled, memory limit exceeded","labels":{"service":"payment","cluster":"c1"},"timestamp":1758209400000}'
# Expected: {"accepted":1,"duplicated":0,"event_id":"...","total":1}

# Batch
curl -X POST http://127.0.0.1:8000/api/v1/ingest/alerts/batch \
  -H "Content-Type: application/json" -H "X-Ingest-Token: <event_ingest_token>" \
  -d '{"events":[{"source":"webhook","raw_message":"..."},{"source":"webhook","raw_message":"..."}]}'
# Expected: {"total":2,"accepted":2,"duplicated":0,"failed":0,"results":[{"event_id":"...","result":"accepted"},...]}
```

### 23.2 Post-diagnosis notification push (console → ITSM/UMPS)

- Trigger points: after a successful single-round diagnosis (`/api/v1/console/events/{id}/diagnose`) or deep-diagnosis Agent (`/api/v1/console/agent/diagnose`) run is persisted; silently skipped when `notify_webhook_url` is not configured.
- Notifications are fire-and-forget background tasks (10s per-call timeout): failures are logged only and never block the diagnosis response or trigger automatic retries; the payload is a snapshot of the persisted terminal state (diagnosed/degraded, etc.).

| Notification field | Description |
|--------------------|-------------|
| source / event_type | Always `rootsleuth` / `diagnosis_completed` |
| event_id / internal_id | External event ID and the console's internal id |
| service_name / cluster / topology / error_type / severity / template / status / degraded_reason | Event metadata snapshot |
| root_cause / solution / command | Diagnosis conclusions (root cause / remediation suggestion / fix command) |
| confidence / trust_index | Confidence and Trust Index (trust_index from ai_output_json.quality) |
| model / diagnosis_source / diagnosed_at | Model, diagnosis pipeline (single_round / agent), and diagnosis time |

- Sample payload:

```json
{
  "source": "rootsleuth",
  "event_type": "diagnosis_completed",
  "event_id": "E2E-EVT-001",
  "internal_id": 51,
  "service_name": "payment",
  "cluster": "c1",
  "error_type": "oom_killed",
  "severity": "critical",
  "template": "OOMKilled",
  "status": "diagnosed",
  "root_cause": "...",
  "solution": "...",
  "command": "...",
  "confidence": 0.86,
  "trust_index": 0.87,
  "model": "<LLM model configured in the config center>",
  "diagnosis_source": "single_round",
  "diagnosed_at": "2026-09-18T09:02:42+00:00"
}
```

- UMPS/ITSM mapping suggestions: `event_id` → external incident correlation key; `severity` → ticket priority (critical → P1/P2); `root_cause` + `solution` → ticket description / remediation plan body; when `confidence` / `trust_index` falls below the thresholds (config center `confidence_threshold` / the 0.85 Trust Index alert line), manual review is recommended.

## 24. Hybrid LLM routing & compliance audit (review adoption)

The diagnosis chain (single-round one-click diagnosis + deep-diagnosis Agent and its degradation paths) performs a three-dimensional routing decision before every LLM call (`app/backend/services/llm_routing.py`); sensitive data is never sent to a remote LLM.

### 24.1 Three-dimensional routing decision

| Dimension | Basis | Decision |
|-----------|-------|----------|
| Data sensitivity | detect_sensitivity: key assignments / Bearer tokens / private IPs (including masked placeholder `a.b.c.x`) / phone numbers / ID cards / long digit runs / emails / long tokens / mask placeholders | Sensitive → forced local |
| Alert severity | events.severity | critical → conservative local handling |
| Service tier | CMDB asset environment (prod / production) | Production → conservative local handling |

- Routing policy `llm_routing_policy`:
  - `auto` (default): non-sensitive + non-critical + non-production + remote approval ID configured → remote; any condition unmet → local;
  - `local_only`: always local; when local LLM is not deployed, degrade to a deterministic conclusion;
  - `remote_only`: always remote, but sensitive data is still forced local (the red line takes precedence).
- Red-line double safeguard: when `llm_remote_approval_id` is empty, remote routing is rejected under any policy and falls back to local.
- Sensitive data + local LLM not configured: all LLM calls are skipped and a deterministic conclusion is built directly from knowledge-base candidates (root cause prefixed "Sensitive data stays on-premises · deterministic conclusion", `degraded_reason=sensitive_local_unavailable_deterministic`); remote fallback never happens.

### 24.2 Local LLM access (Ollama / vLLM, OpenAI-compatible endpoints)

### 24.3 Compliance audit hash chain & tamper verification

- The two audit record types — routing decisions (`llm_route_decision`) and LLM calls (`llm_invocation`) — form a hash chain: the existing `audit_logs` table is reused (chain fields stored in `after_json.chain` as `prev_hash` / `hash`, **no table schema change**), with `hash = sha256(prev_hash | actor | action | target_type | target_id | normalized after JSON)`; audit content records only sensitivity category labels and routing metadata, never raw alert text.
- Tamper verification (sys_admin): if any record's `after_json` is tampered with, the whole chain fails verification and the first broken link is pinpointed.

# Expected: {"ok":true,"total":N,"head_hash":"...","broken_id":null}

## 25. Data classification & inbound masking (review adoption)

The event ingest API (`POST /api/v1/ingest/alerts`) enables inbound masking by default (`data_masking_enabled=true`): raw alert text is masked via `mask_alert_text` before persistence, and **raw content is never stored**.

| Category | Example | Masked |
|----------|---------|--------|
| ID card | 11010119900307851X | 110****851X |
| Phone number | 13812345678 | 138****5678 |
| Bank card / long digits (15~19) | 6222020200112233 | 6222****2233 |
| Private IP | 10.1.2.3 / 192.168.1.100 | 10.1.2.x / 192.168.1.x |
| Key assignment | password=Sup3rSecret | password=*** |
| Bearer token | Bearer abc.def-ghi | Bearer *** |
| Email | user@example.com | ***@*** |
| Long token (≥32 chars) | eyJhbGciOiJSUzI1NiJ9... | *** |

- Mask placeholders preserve a recognizable format, and `detect_sensitivity` can re-classify persisted text to drive LLM routing (§24.1);
- Public IPs and hostnames are preserved (needed for diagnosis and CMDB correlation);
- Only explicitly setting `data_masking_enabled=false` stores raw text (an explicit deployer choice; the `event_ingest` audit records `data_masking_enabled=false` for traceability);
- Verification: after pushing an alert containing sensitive fields, query the event detail — `raw_log` should only show mask placeholders.

Dedicated regression: `app/backend/tests/test_llm_routing_compliance.py` (15 cases: routing matrix / sensitive-data non-egress / per-category masking / hash-chain tamper detection / ingest integration / route passthrough).
